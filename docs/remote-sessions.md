# Remote sessions

A connected Tailcat session shows up in the bot panel under Sessions à distance and as a card in the chat. The section is always in the panel: with no session it says so in one line. Each row shows the computer, the user, the support code and the end time, with Prendre le contrôle and Fermer la session (a second click confirms). The card lists the computer (name, user, rights, support code, end time, serial, model, processor, memory, disk) and short diagnostic hints. The hints send a prompt. They do not run a command by themselves.

Shell opens the existing in-chat terminal on that computer. Send a file (up to 8 MB) and Download move one file through the tunnel. Prendre le contrôle, from the panel row or the card, opens the Computer tab in Simple and in Advanced alike; it shows a read-only screenshot of the same session. Live mouse and keyboard control will be added over that same picture (`RemoteSessionScreen`), not as another tab. Closing the session asks the end-user script to stop, then marks the card closed.

The tunnel address and the client key stay in the Flow session folder (`$PX_FLOW_HOME/tailcat/<12 hex>/`, default `~/.pulsatrix-flow`). Sagax reads that folder on this host. They are never tool arguments, never API fields, and never shown. If the folder is missing, the card can still show the facts the bot supplied, and shell, files and the screenshot say the tunnel is not on this server.

A session the bot opens with `remote_support_open` (the agents catalog tool, or a Perspicax profile the engine mounts) is registered by Sagax itself: every `remote_support_*` answer passes through `PerspicaxMcp.relay`, and `server/remote-session-register.ts` posts the card and the panel row as soon as `remote_support_status` says connected, and marks it closed on `remote_support_close`. The session id, rights, OS and end time come from the open call; nothing reads the address from a tool answer. For a session Sagax opened, the tunnel is in `<data dir>/remote-support/sessions/<CODE>/` with the technician key beside it. When the OS was not named, Sagax asks the computer (`uname -s`, Windows when there is none; a failed tunnel, exit 255, is asked again at the next publish), outside the store's lock. A session a Flow skill opened is posted with `publish_remote_session` once the end user is connected.

A session belongs to the person whose Perspicax credentials opened it, and to that bot. `remote_support_open` writes `principalId` and `botId` into `sessions/<CODE>/open.json` (the server names them in its answer to the proxy). A tunnel resolves only through the row's own code folder, whose `session` file holds the row's id and whose owner matches the row's person and bot; a folder without an owner never resolves. The 12-hex id is on the chat card, so it is useless on its own: `publish_remote_session` and a direct open refuse an id another person or bot opened, the registrar and its restart recall follow the speaking person (never the conversation owner), and the end time is bounded to 26 hours on every path. Fermer la session in the panel also calls `remote_support_close` as the person closing, deletes the local `address` file, and a later "connected" status does not re-open the card. A Flow session folder (`~/.pulsatrix-flow/tailcat/<id>`) carries no owner yet: on a shared server, only the first person to publish its id gets it.

## The fast process the bot follows

1. A session without administrator rights by default. Elevated only when the person asks.
2. At most three calls: `remote_support_open`; when the person says the script is launched, `remote_support_status` (fetch_ip_count must be exactly 1, one address took the script); that same status connects and marks the session connected (once more if it still says started). No schema search, no cloud fallback.
3. The first reply holds the link, the code and the normal PowerShell line in a `powershell` code fence, exactly as the tool gave it. The line never goes through a shell on this computer: a Mac shell eats its `$` variables.
4. No screenshot written to the Desktop, no Preview: the screen is drawn in Sagax.
5. Never expose the person's own computer: no `tailcat serve`, no exit node, no file sharing, no tunnel back to it. A shell request that names no other destination opens the remote terminal at once.

Sagax ships tailcat 0.7.0 beside the app and in the server image. It runs that copy, then a copy under its data directory, then Homebrew or `/usr/local/bin`. A tailcat on the default system PATH is not required, and Sagax does not download one at runtime. The server image and the cloud computer image bake the Linux binary into `/usr/local/bin`. A cloud computer that is already running does not see it until that image is rebuilt and published.
